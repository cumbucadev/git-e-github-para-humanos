# 5.6 O que é importante levar deste capítulo

Neste capítulo, o ponto principal foi ajustar o significado de **salvar** no contexto do Git.

Salvar não é sobrescrever um arquivo. Também não é sair duplicando pastas com “Salvar como”. Salvar é registrar um **estado completo** do projeto em um instante no tempo. Pense em **checkpoints**. Você cria um ponto seguro. Depois, você consegue voltar nele.

Alguns pontos importantes para guardar:

* **O Git preserva versões.**\
  Cada salvamento cria um novo “marco” na história. O passado não é substituído.
* **As mudanças passam por áreas, não por um botão mágico.**\
  Você trabalha no Working Directory. Você organiza na Staging Area. Você preserva no Repository (histórico).
* **A Staging Area é uma escolha intencional.**\
  Você decide o que entra na próxima versão. Nem tudo precisa ir junto.
* **Nem todo arquivo na pasta está sendo versionado.**\
  Estar no diretório não significa estar sob controle do Git.
* **Arquivos podem estar em três “visões” para o Git.**
  * **untracked:** existe na pasta, mas o Git ainda não acompanha.
  * **tracked:** o Git acompanha e detecta mudanças.
  * **ignored:** você pediu para o Git fingir que não existe.

Se você sair daqui entendendo **checkpoint**, **áreas locais** e **rastreamento**, você está no caminho certo. No próximo capítulo, vamos começar a colocar esse fluxo em prática com comandos.
