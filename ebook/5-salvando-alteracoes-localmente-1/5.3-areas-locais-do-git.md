# 5.3 Áreas locais do Git

Para que o Git consiga registrar os estados de um projeto, as mudanças não vão diretamente dos arquivos modificados para o histórico. Elas percorrem um pequeno caminho, um fluxo que organiza como cada alteração é tratada.

Em vez de pensar apenas em “arquivos salvos” ou “arquivos não salvos”, é mais preciso imaginar que o Git trabalha com mudanças em diferentes estágios. Esses estágios correspondem às três áreas do sistema: **Working Directory**, **Staging Area** e **Repository**.

## Working Directory

Tudo começa no **Working Directory**, também chamado de diretório de trabalho ou _working tree_. Essa é a área mais familiar, pois corresponde exatamente aos arquivos que você vê e edita na sua máquina.

É aqui que você escreve código, altera textos, cria arquivos e realiza qualquer modificação. Nesse estágio, as mudanças existem apenas como rascunho. Elas ainda não fazem parte de um estado registrado do projeto.

Quando um arquivo é alterado, o Git reconhece que houve mudanças, mas não assume automaticamente que elas devem ser preservadas. Antes disso, existe uma etapa intermediária.

## Staging Area

Depois que as mudanças surgem no working directory, elas podem seguir para a próxima área do Git: a **Staging Area**, também conhecida como área de preparação ou _index_.

A staging area funciona como um espaço de organização. Em vez de registrar todas as alterações feitas no working directory, você escolhe quais mudanças deseja preparar.

Esse é um dos pontos mais importantes do Git. Você não está movendo arquivos, mas selecionando mudanças. É como revisar um rascunho antes de torná-lo parte da história do projeto.

Nesse estágio, as alterações deixam de ser apenas edições em andamento e passam a compor a próxima versão que será registrada. Depois de organizadas, as mudanças seguem para o repository.

## Repository

O **Repository** é a área onde os estados do projeto são armazenados. Ele reside dentro da pasta oculta `.git` e representa o histórico propriamente dito.

Quando as mudanças chegam aqui, o estado do projeto é preservado. Nesse ponto, podemos pensar que temos uma versão publicada do projeto. Não se trata mais de um rascunho nem de algo em preparação, mas de um estado que passa a fazer parte da história e pode ser revisitado sempre que necessário.

***

Desta forma, o fluxo do Git pode ser descrito a partir de três áreas principais. O **Working Directory** representa a versão em rascunho, onde o trabalho acontece. A **Staging Area** corresponde à etapa de preparação, em que as mudanças são organizadas. O **Repository**, por sua vez, representa a versão preservada, onde o estado passa a fazer parte da história do projeto.

Essa separação é uma das ideias centrais do Git. Ela permite um controle muito mais preciso sobre o que é registrado, evita alterações acidentais e estabelece uma estrutura clara para a construção das versões.

Compreendidas essas áreas, o próximo passo é entender como as mudanças percorrem esse caminho na prática. É isso que veremos na próxima seção.
